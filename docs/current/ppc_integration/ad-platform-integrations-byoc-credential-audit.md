# Ad Platform Integrations Credential Audit — Multi-Tenant BYOC Model

**Project:** CHERP / ERP Ad Platform Integrations  
**Module audited:** `frontend/src/features/integrations/AdIntegrationsPage.tsx`  
**Branch context:** `ui-animations-reactlib`  
**Date:** 2026-08-31  
**Architecture assumption:** Multi-tenant SaaS, where each agency/client/tenant brings their own ad platform credentials and connects their own ad accounts.

---

## 1. Executive Verdict

The current implementation is directionally right in supporting OAuth, but the credential model is wrong for a proper multi-tenant setup because it mixes different platform concepts into a generic form:

```ts
client_id
client_secret
developer_token
account_id
```

This is not enough because every platform has a different distinction between:

1. **Tenant-owned developer app credentials** — values the client/tenant gets from Meta Developers, Google Cloud Console, LinkedIn Developer Portal, or Google Cloud / GAM setup.
2. **OAuth user/account authorization** — access token, refresh token, expiry, scopes, authorized user/account identity.
3. **Ad account / network identifiers** — the actual advertising account or network to pull data from.
4. **Backend operational metadata** — connection status, validation errors, token refresh status, last sync, etc.

For your SaaS model, CHERP should **not use one global backend key for all clients**. Each tenant should be allowed to configure their own platform credentials and then authorize their own ad accounts through OAuth. The backend should only provide the connection infrastructure, callback routes, encryption, validation, token refresh, account discovery, and sync jobs.

## 2. Correct Multi-Tenant Credential Principle

### Correct Principle

Each tenant/client should have an isolated connection record per platform:

```text
Tenant A -> Meta App A -> Tenant A OAuth token -> Tenant A Meta Ad Account(s)
Tenant B -> Meta App B -> Tenant B OAuth token -> Tenant B Meta Ad Account(s)
Tenant C -> Google Ads OAuth Client C -> Tenant C Google Ads Account(s)
```

### Incorrect Principle

This is not acceptable for the target architecture:

```text
CHERP Backend -> One Meta App / One Google Ads App / One LinkedIn App -> All client accounts
```

That model creates operational, compliance, review, access-tier, and permission problems. It also breaks your stated requirement that separate users/clients should bring their own keys and connect their own ad accounts.

## 3. Current UI / Code Issue Observed

The current page defines per-platform `keyFields`, but still renders a generic manual credential form for all platforms.

Current manual form state:

```ts
const [keyForm, setKeyForm] = useState({
  client_id: '',
  client_secret: '',
  developer_token: '',
  account_id: '',
})
```

Current save payload:

```ts
await apiClient.post('/ad-platform/credentials', {
  platform: selectedPlatform,
  client_id: keyForm.client_id.trim() || undefined,
  client_secret: keyForm.client_secret.trim() || undefined,
  developer_token: keyForm.developer_token.trim() || undefined,
  account_id: keyForm.account_id.trim() || undefined,
  is_enabled: true,
})
```

### Why this is wrong

The same four fields cannot correctly represent Meta Ads, Google Ads, LinkedIn Ads, and Google Ad Manager.

For example:

- `developer_token` is valid for **Google Ads**, not Meta Ads, LinkedIn Ads, or GAM.
- `account_id` is too generic. It could mean Meta Ad Account ID, Google Ads Customer ID, LinkedIn Sponsored Account URN, or GAM Network Code.
- `client_id` and `client_secret` mean different things depending on the platform:
  - Google Ads: OAuth Client ID / Secret.
  - LinkedIn Ads: OAuth Client ID / Secret.
  - Meta Ads: App ID / App Secret.
  - GAM: OAuth Client ID / Secret or Service Account JSON depending on auth mode.
- `client_secret` must never be exposed after saving and should never be treated as a normal visible editable value.
- OAuth tokens should not be manually pasted by users. They should be generated by OAuth callback and stored encrypted.

## 4. Correct Data Model for Multi-Tenant BYOC

### 4.1 Tenant Platform App Credentials

This table stores developer/app credentials brought by each tenant.

```ts
type AdPlatform =
  | 'META_ADS'
  | 'GOOGLE_ADS'
  | 'LINKEDIN_ADS'
  | 'GOOGLE_AD_MANAGER'

type TenantAdPlatformAppCredential = {
  id: string
  tenantId: string
  platform: AdPlatform

  // Platform-specific developer/app credentials
  appId?: string                 // Meta App ID
  appSecretEncrypted?: string    // Meta App Secret

  oauthClientId?: string         // Google Ads, LinkedIn, GAM web OAuth
  oauthClientSecretEncrypted?: string
  redirectUri?: string

  developerTokenEncrypted?: string // Google Ads only

  serviceAccountEmail?: string       // GAM service account mode only
  serviceAccountJsonEncrypted?: string // GAM service account JSON only
  applicationName?: string           // GAM request header/client config

  requestedScopes: string[]
  authMode: 'OAUTH_WEB' | 'SERVICE_ACCOUNT'

  status: 'DRAFT' | 'READY' | 'INVALID'
  lastValidatedAt?: Date
  validationErrorCode?: string
  validationErrorMessage?: string

  createdAt: Date
  updatedAt: Date
}
```

### 4.2 Tenant OAuth Connection

This table stores OAuth authorization generated after the tenant connects an account.

```ts
type TenantAdPlatformOAuthConnection = {
  id: string
  tenantId: string
  platform: AdPlatform
  appCredentialId: string

  authorizedUserId?: string
  authorizedEmail?: string

  accessTokenEncrypted?: string
  refreshTokenEncrypted?: string
  tokenType?: string
  tokenExpiresAt?: Date
  grantedScopes: string[]

  status: 'CONNECTED' | 'EXPIRED' | 'REVOKED' | 'FAILED'
  lastRefreshAt?: Date
  lastValidatedAt?: Date
  errorCode?: string
  errorMessage?: string

  createdAt: Date
  updatedAt: Date
}
```

### 4.3 Linked Ad Account / Network

This table maps actual ad accounts to CHERP clients/brands.

```ts
type TenantLinkedAdAccount = {
  id: string
  tenantId: string
  cherpClientId?: string
  platform: AdPlatform
  oauthConnectionId?: string

  // Platform-specific account identifiers
  metaAdAccountId?: string          // act_123456789 or normalized from numeric ID
  googleAdsCustomerId?: string      // 10-digit, no dashes
  googleAdsLoginCustomerId?: string // optional MCC manager ID, no dashes
  linkedinSponsoredAccountUrn?: string // urn:li:sponsoredAccount:{id}
  gamNetworkCode?: string

  accountName?: string
  currencyCode?: string
  timezone?: string
  isActive: boolean

  lastSyncAt?: Date
  syncStatus: 'NEVER_SYNCED' | 'SYNCING' | 'SYNCED' | 'FAILED'
  syncErrorCode?: string
  syncErrorMessage?: string

  createdAt: Date
  updatedAt: Date
}
```

## 5. Platform-by-Platform Required Credentials

## 5.1 Meta Ads Manager

### Correct Multi-Tenant Flow

Each tenant creates their own Meta Developer App and connects their own Meta ad accounts.

### Tenant-provided app credentials

| Field | Required? | Stored Where? | Notes |
|---|---:|---|---|
| Meta App ID | Yes | Tenant app credential table | Public-ish identifier, but still tenant-scoped. |
| Meta App Secret | Yes | Encrypted server-side | Never expose after saving. |
| Redirect URI | Yes | Tenant app credential table or derived per tenant | Must match Meta app OAuth settings. |
| Requested scopes | Yes | Tenant app credential table | Usually `ads_read`; `ads_management` only if creating/updating campaigns. |
| Business Manager ID | Optional | Tenant metadata | Helpful for discovery/validation, not the same as ad account ID. |

### OAuth-generated values

| Field | Required? | How obtained? | Notes |
|---|---:|---|---|
| User access token | Yes | OAuth callback | Do not ask user to paste this manually. |
| Long-lived access token / refreshed token | Usually yes | Token exchange/refresh flow | Store encrypted. |
| Granted scopes | Yes | OAuth callback / debug endpoint | Use to verify permissions. |

### Account values

| Field | Required? | Notes |
|---|---:|---|
| Meta Ad Account ID | Yes | Format should be normalized as `act_<AD_ACCOUNT_ID>`. |
| Account name | Optional | Can be discovered after token validation. |
| Currency / timezone | Optional | Can be discovered after account fetch. |

### Wrong current field usage

| Current / generic field | Verdict | Correction |
|---|---|---|
| `client_id` | Misleading | Rename to `appId` for Meta. |
| `client_secret` | Misleading but conceptually valid | Rename to `appSecretEncrypted`; never show after save. |
| `developer_token` | Wrong | Meta does not use Google Ads-style developer tokens. |
| `account_id` | Too generic | Split into `metaAdAccountId` and optional `businessManagerId`. |
| Manual access token | Should not be collected | Use OAuth callback. |

## 5.4 Google Ad Manager (GAM)

### Correct Multi-Tenant Flow

Each tenant connects their own GAM network. For a multi-tenant SaaS, there are two acceptable tenant-specific patterns:

1. **Tenant-owned OAuth web app credentials** — tenant creates OAuth client and authorizes the user/network.
2. **Tenant-owned service account credentials** — tenant creates a service account, enables API access, adds that service account user to the GAM network, and uploads/provides the service account JSON securely.

Since your requirement is BYOC, CHERP should support tenant-level GAM credentials. A single backend service account for all tenants should not be assumed.

### Tenant-provided credentials — OAuth web app mode

| Field | Required? | Stored Where? | Notes |
|---|---:|---|---|
| OAuth Client ID | Yes | Tenant app credential table | From Google Cloud Console. |
| OAuth Client Secret | Yes | Encrypted server-side | Never expose after saving. |
| Redirect URI | Yes | Tenant app credential table or derived per tenant | Must match Google Cloud app. |
| GAM API scope | Yes | Tenant app credential table | `https://www.googleapis.com/auth/dfp`. |
| Application Name | Yes | Tenant app credential table | Required/configured in GAM API client/request flow. |

### Tenant-provided credentials — Service account mode

| Field | Required? | Stored Where? | Notes |
|---|---:|---|---|
| Service Account Email | Yes | Tenant app credential table | Must be added as a GAM user. |
| Service Account JSON / Private Key | Yes | Encrypted server-side | Treat as highly sensitive. |
| GAM Network Code | Yes | Linked ad account/network table | Found in GAM URL, e.g. `https://admanager.google.com/1234#home`. |
| Application Name | Yes | Tenant app credential table | GAM client config/request header. |
| API Access Enabled | Yes | Validation requirement | Tenant must enable API access in GAM network. |

### OAuth-generated values, if OAuth web app mode is used

| Field | Required? | How obtained? | Notes |
|---|---:|---|---|
| Access token | Yes | OAuth callback / refresh | Store encrypted. |
| Refresh token | Yes for durable sync | OAuth callback | Store encrypted. |
| Granted scopes | Yes | OAuth callback | Validate `dfp` scope. |

### Account/network values

| Field | Required? | Notes |
|---|---:|---|
| GAM Network Code | Yes | This is not a Google Ads Customer ID. |
| Network display name | Optional | Can be discovered. |

### Wrong current field usage

| Current / generic field | Verdict | Correction |
|---|---|---|
| `client_id` | Valid only in OAuth web app mode | Rename to `oauthClientId`; not used in service-account mode. |
| `client_secret` | Valid only in OAuth web app mode | Rename to `oauthClientSecretEncrypted`; not used in service-account mode. |
| `developer_token` | Wrong | GAM does not use Google Ads developer token. |
| `account_id` | Wrong / ambiguous | Rename to `gamNetworkCode`. |
| Generic `Manager Account ID` label | Wrong | GAM needs `networkCode`, not MCC ID. |

## 8. Required UX Change

### Current UX Problem

The UI currently offers:

```text
One-Click OAuth 2.0
Manual API Keys
```

But the manual form is not platform-aware enough and asks for generic fields.

### Correct UX for BYOC

Use a two-step setup per platform:

```text
Step 1: Tenant enters platform developer/app credentials.
Step 2: Tenant starts OAuth authorization using those credentials.
Step 3: CHERP receives callback, stores encrypted OAuth tokens.
Step 4: CHERP discovers accessible ad accounts/networks if possible.
Step 5: Tenant maps selected ad accounts to CHERP clients/brands.
Step 6: CHERP validates and marks connection as CONNECTED.
```

### Correct UI Sections

For each platform, show:

1. **Developer App Credentials**
   - Tenant enters app/client/service credentials.
   - Secrets are write-only after save.
   - Backend validates configuration.

2. **Connect Ad Account**
   - Starts OAuth using tenant’s stored credentials.
   - No manual token input.

3. **Discovered Accounts / Manual Fallback**
   - Meta: select or enter `act_<id>`.
   - Google Ads: select or enter `customerId`; optional `loginCustomerId`.
   - LinkedIn: select or enter Sponsored Account URN.
   - GAM: enter/select `networkCode`.

4. **Test Connection**
   - Verify token, scopes, account access, and sample reporting endpoint.

## 9. Backend Changes Required

### Required Endpoints

```http
POST /ad-platform/app-credentials
GET  /ad-platform/app-credentials
PATCH /ad-platform/app-credentials/:id
POST /ad-platform/app-credentials/:id/validate

GET  /ad-platform/oauth/:platform/start?appCredentialId=...
GET  /ad-platform/oauth/:platform/callback

GET  /ad-platform/accounts/:platform?connectionId=...
POST /ad-platform/linked-accounts
POST /ad-platform/linked-accounts/:id/test
POST /ad-platform/linked-accounts/:id/sync
```

### Required Backend Behaviors

- Store all secrets encrypted at rest.
- Never return secrets to frontend after saving.
- OAuth state must include `tenantId`, `platform`, `appCredentialId`, nonce, and CSRF protection.
- OAuth callback must resolve the correct tenant app credential, not a global provider config.
- Token refresh jobs must run per tenant connection.
- Sync jobs must be scoped by `tenantId` and `linkedAdAccountId`.
- Validation errors must be stored with `errorCode` and `errorMessage`.
- Account IDs must be normalized per platform before saving.

## 11. Updated Implementation Verdict

### Do not remove BYOC credentials entirely

Because your SaaS is multi-tenant and each client brings their own ad accounts, you **do need tenant-level credentials**.

The correction is not:

```text
Remove all app credentials from client setup and only use backend env values.
```

The correction is:

```text
Move credentials into tenant-scoped encrypted records, make them platform-specific, and use them to run OAuth/account linking per tenant.
```

### Correct final design

```text
Tenant enters platform app credentials
        ↓
Backend encrypts and validates credentials
        ↓
Tenant clicks Connect OAuth
        ↓
OAuth callback stores tenant-specific tokens
        ↓
Backend discovers accessible accounts/networks
        ↓
Tenant maps ad account to CHERP client/brand
        ↓
CHERP syncs reporting data per tenant connection
```

## 13. Source Verification Notes

The following public documentation was used to verify required fields and concepts:

- Google Ads API authorization requires OAuth2 credentials, access token flow, and the `developer-token` header. `login-customer-id` is needed when accessing a client account through a manager account.
- Google Ads customer IDs should be stored without dashes.
- Google Ad Manager requires OAuth2 authorization, network API access, `networkCode`, and `applicationName`; service account mode requires service account credentials and the service account user must be configured in GAM.
- LinkedIn Marketing APIs use OAuth2 authorization and require approved Advertising API permissions such as `r_ads`, `r_ads_reporting`, and `rw_ads` depending on the use case.
- Meta Marketing API requires a Meta app, Marketing API product, a user access token with advertising permissions such as `ads_read` / `ads_management`, and an ad account ID in `act_<AD_ACCOUNT_ID>` format.

## 14. Final Recommendation

Build the integration module as a **Tenant-Owned Credentials + OAuth Connection + Linked Account Mapping** system.

Do not use a single backend-owned credential set for all tenants.

Do not use one generic credential form for every platform.

Do not ask users to paste OAuth access tokens manually.

Do use per-tenant encrypted platform credentials, per-tenant OAuth token records, and per-platform account identifier fields.
